## Офлайн-каталог MVP

Издатель Scento публикует CSV и JSONL. Снимок от 2026-10-29 содержит 1 479 записей ароматов по опубликованному описанию. По политике происхождения Scento проверяет фактические сведения по страницам домов и авторизованных продавцов, пишет описания самостоятельно и не включает сторонние исходные тексты. У каждой строки есть URL записи каталога. Снимок подходит как каталог ароматов и нот. Правила живого API действуют отдельно. [Публикация издателя](https://www.scento.com/perfume-database), [форматы, поля и политика происхождения](https://github.com/Scento-com/perfume-dataset#sources-policy).

При импорте фиксировать дату снимка, идентификатор версии или коммита, контрольную сумму файла, исходные `id` и `url`, лицензию и применённые преобразования. Для распространения производных данных сохранять атрибуцию «Scento — https://www.scento.com/perfume-database», ссылку на CC BY 4.0 и указание изменений, включая отбор и нормализацию. Привязать атрибуцию к показу данных и экспорту. Пустые год, парфюмер и уровни пирамиды считать неизвестными. [Атрибуция издателя](https://github.com/Scento-com/perfume-dataset#license-and-attribution), [условия лицензии](https://creativecommons.org/licenses/by/4.0/).

В выгрузке нет оценок и голосов Fragrantica, российских отзывов, блогерских мнений, магазинных офферов или изображений флаконов. Ссылки на страницы не дают прав на их фотографии. `popularity_rank` означает известность в каталоге Scento, где 1 — самый известный. Использовать его можно как отдельно названный показатель известности с происхождением, сохраняя исходную шкалу и версию снимка. Методика расчёта ранга в схеме не раскрыта. При отсутствии данных F, R, B и зависимый от них C остаются недоступными, веса перераспределяются по правилам проекта. При показе карточки явно обозначать пробелы. [Схема снимка](https://github.com/Scento-com/perfume-dataset#fields), [границы лицензии](https://creativecommons.org/licenses/by/4.0/).

## Тексты обзоров, цитаты и удаление

- YouTube API Developer Policies §III.E.3 ограничивают доступ к Authorized Data авторизовавшим пользователем и его явно одобренными представителями. §III.E.4.h ограничивает производные данные и метрики. Дополнительная программа действует по отдельному одобрению для аналитики, перечисляет конкретные сценарии и не подтверждает право проекта передавать субтитры в OpenAI или рассчитывать по ним оценку ароматов. До включения такого сценария нужны письменное разрешение платформы на операции с API Data и права автора на передачу и цитирование. Альтернатива для последующего согласования — получить исходный текст напрямую от автора вне API, отдельно согласовав его использование, обработку у провайдера, срок хранения и допустимые цитаты. Хранимые API Data подчиняются §III.E.4 и §III.D.3, включая правила обновления или удаления через 30 дней для указанных категорий, удаление по запросу в пределах 7 календарных дней и сроки при отзыве доступа. [Политики API](https://developers.google.com/youtube/terms/developer-policies), [дополнительные политики производных метрик](https://developers.google.com/youtube/terms/derived-metrics-policy), [права на контент YouTube](https://www.youtube.com/t/terms).
- Получение реакций пользователя через Bot API — отдельный поток от чтения каналов. До включения определить понятную политику конфиденциальности, минимальный набор хранимых полей, удаление по запросу и после утраты цели, шифрование пользовательских данных в покое с отдельным хранением ключа. Реакции, профиль вкуса, идентификаторы чатов и пользователей обрабатываются локально. [Условия разработчиков ботов, §§4–4.5](https://telegram.org/tos/bot-developers).
- Отзывы и цитаты подключать отдельно по каждому источнику после подтверждения прав и opt-in. Условия должны охватывать получение, хранение, цель обработки, передачу провайдеру, производные данные, цитаты и удаление. При отсутствии разрешения хранить только допустимую ссылку и собственные сведения. Не публиковать цитату до подтверждения прав на неё. Удаление источника или отзыв разрешения должен охватывать локальные выдержки, результаты и индекс. Правило очистки кэша описано ниже.
- Товарный фид открывать отдельно после проверки разрешённых каналов публикации, полей, лимитов и частоты обновления. Ручная запись связывает ссылку с датой проверки. Цена, остаток и формат неизвестны, если не проверены. Скрейпинг страниц и угадывание наличия исключены.

## Обработка в OpenAI

- Для двух операций — извлечения упоминаний и резюме — использовать Responses API со строгой JSON Schema в `text.format` (`type: json_schema`, `strict: true`). Валидировать результат, обрабатывать отказ и неполный ответ. Передавать только минимально необходимый разрешённый фрагмент и допустимые справочные поля. Не включать полные тексты, пользовательские идентификаторы, персональные данные, токены и приватные сообщения. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
- Явно задавать `store=false` в каждом синхронном текстовом запросе. Для этого сценария не использовать фоновые запросы, файлы, Conversations и внешние инструменты. `store=false` отключает обычное сохранение ответа для последующего получения. Журналы мониторинга злоупотреблений могут содержать вход и выход и по умолчанию хранятся до 30 дней с оговорёнными исключениями. Zero Data Retention требует отдельного одобрения и настройки. API-данные по умолчанию не используются для обучения моделей. [Data controls](https://developers.openai.com/api/docs/guides/your-data), [миграция на Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses).
- Кэшировать разрешённые структурированные результаты локально по хэшу входа с версией модели, схемы и промпта. Не хранить необработанный текст в кэше и логах. Пока кэш не хранит связь с источником, при отзыве разрешения или истечении разрешённого срока остановить обработку и выдачу затронутых данных, полностью очистить локальный LLM-кэш и удалить связанные результаты и выдержки по их происхождению до возобновления работы. В логах оставлять имя источника, класс события, статус и числовые метрики без данных пользователя, тела запроса, ответов, секретов, идентификаторов сессии и URL с ключами. [OpenAI DPA, §§2.11 и 3.3](https://openai.com/policies/data-processing-addendum/), [безопасность API-ключей](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety).
- Проверить, что развёртывание, доступ и предоставление доступа укладываются в поддерживаемую географию OpenAI. Российская Федерация отсутствует в списке на дату проверки. При доступе или предоставлении доступа из РФ живой вызов закрыт. Часовой пояс рассылки `Asia/Omsk` сам по себе не устанавливает место доступа. [Список стран и территорий](https://developers.openai.com/api/docs/supported-countries), [OpenAI Services Agreement, §16.12](https://openai.com/policies/services-agreement/).
